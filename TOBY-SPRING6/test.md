# 테스트

## 1. 자동으로 수행되는 테스트(Automated Test)

- 수동으로 애플리케이션 코드를 검증하는 방식은 번거롭고 반복 실행에 한계가 있다.
- **코드로 작성되어 언제든 반복 실행 가능한 자동화된 테스트**를 구축해야 지속적인 코드 개선과 점진적인 기능 확장이 가능하다.

## 2. 개발자가 만드는 테스트

- 테스트 코드를 직접 작성하고 자동화된 테스트를 실행하여 작성한 코드의 동작 결과를 신속하게 피드백받는다.
- 테스트의 작성과 실행을 별도 단계가 아닌 일상적인 개발 작업 흐름의 핵심 과정으로 편입한다.
- xUnit 계열의 테스팅 프레임워크를 활용하여 테스트 작성 및 실행 전반을 체계적이고 효율적으로 관리한다.

## 3. JUnit 테스트 작성

- JUnit은 켄트 벡(Kent Beck)과 에릭 감마(Erich Gamma)가 개발한 자바 진영의 대표적인 단위 테스트 프레임워크이다.
- 다른 프로그래밍 언어로도 유사한 구조의 테스팅 도구들이 널리 파생되었으며, 이를 총칭하여 **xUnit**이라 부른다.
- **JUnit 5**
  - 자바 표준 테스팅 프레임워크의 최신 버전이다.
  - 스프링 프레임워크 자체의 내부 테스트뿐만 아니라 스프링 기반 프로젝트 전반에서 사실상 표준으로 사용된다.

## 4. 자동화된 테스트의 어려움

- 자동화된 테스트는 실행 시점과 환경에 무관하게 항상 일관된 결과를 도출해야 한다.
- 외부 API 연동이나 현재 시간, 난수 생성 등 실행 환경에 따라 제어하기 어려운 요소를 포함할 경우 결정론적(Deterministic)인 테스트 코드를 작성하기 어렵다.
- **테스트 대상 시스템(System Under Test, SUT)**
  - 테스트의 직접적인 대상이 되는 클래스, 모듈 또는 시스템 전체를 의미한다.

## 5. 테스트와 DI

- **테스트 대역(Test Double)**
  - 제어하기 어려운 외부 의존성을 격리하기 위해 실제 오브젝트를 대체하는 가짜 객체를 **테스트 대역(Test Double)**이라고 부른다.
  - 테스트에 필요한 사전 상태나 고정된 반환값을 제공하는 **스텁(Stub)**과, 메소드 호출 여부 및 행위 검증을 담당하는 **목(Mock)** 등을 활용한다.
- **스프링 DI를 이용하는 통합 테스트**
  - 스프링 컨테이너를 구동하여 테스트 대상과 의존 빈 오브젝트를 설정하고, 컨테이너에서 관리되는 빈을 주입받아 테스트를 수행할 수 있다.
  - 스프링은 통합 테스트를 지원하기 위한 풍부한 테스트 전용 기능을 프레임워크 차원에서 제공한다.
- **스프링 테스트 애노테이션**
  - **@ExtendWith**
    - JUnit 5의 확장 모델을 적용하여 테스트 클래스가 스프링의 테스팅 컨텍스트 프레임워크와 연동되도록 지정한다.
    - `@ContextConfiguration`과 결합된 합성 애노테이션인 `@SpringJUnitConfig`를 주로 활용한다.
  - **@ContextConfiguration**
    - 테스트용 스프링 컨테이너를 구성할 설정 파일 경로(`XML`)나 설정 클래스(`@Configuration`) 정보를 지정한다.
  - **@Autowired**
    - 테스트 클래스의 인스턴스 필드에 선언하면 테스트 컨텍스트에 의해 타입이 일치하는 스프링 컨테이너 내부의 빈 오브젝트가 자동 주입된다.

## 6. 학습 테스트(Learning Test)

- **학습 테스트는 개발자 자신이 직접 작성하지 않은 외부 코드, 라이브러리, 프레임워크, API 등을 검증하는 테스트이다**.
- 사용할 외부 라이브러리나 기술의 동작 방식을 직접 테스트 코드로 작성하고 실행해 보며 올바른 사용법과 기능을 명확히 파악하는 데 목적이 있다.
- 켄트 벡의 『테스트 주도 개발』과 로버트 마틴(Robert C. Martin)의 『클린 코드』에서 기술 학습 및 프레임워크 버전 업그레이드 검증 도구로 권장하는 테스트 기법이다.
