# 서비스 추상화

## 1. 서비스

- 서비스는 범용적인 용어로 사용되는 맥락과 아키텍처 계층에 따라 다양한 의미를 갖는다.
- 기본적으로 **클라이언트(호출자)에게 특정 기능을 제공하는 오브젝트 또는 모듈을 의미**한다.
- 서비스를 요청하는 클라이언트가 존재하지 않는 서비스는 성립하지 않는다.
- 서비스 오브젝트는 일반적으로 내부 상태를 유지하지 않는 **무상태(Stateless)** 특성을 가진다.
- 상태를 공유하지 않으므로 멀티스레드 환경에서 안전한 싱글톤 스프링 빈(`@Component`, `@Service`)으로 등록해 사용하기 적합하다.
  - 예를 들어 회원 서비스(`MemberService`)는 특정 회원의 상태 정보를 필드에 보관하지 않고 비즈니스 연산 로직만 수행하므로 무상태성을 유지한다.

## 2. 서비스의 종류

- **애플리케이션 서비스(Application Service)**
  - 애플리케이션 계층에 위치하며 유스케이스 흐름 제어, 트랜잭션 경계 설정, 보안 처리 등을 담당한다.
  - 스프링에서는 주로 `@Service` 애노테이션을 부여하여 컴포넌트로 관리한다.
- **도메인 서비스(Domain Service)**
  - 도메인 주도 설계(DDD)의 도메인 모델 패턴 적용 시, 특정 엔티티나 밸류 타입 하나에 책임을 귀속시키기 모호한 비즈니스 로직을 처리한다.
  - 여러 도메인 객체 간의 상호작용이나 복합적인 비즈니스 규칙 연산을 캡슐화한다.
- **인프라 서비스(Infrastructure Service)**
  - 핵심 비즈니스(도메인/애플리케이션) 로직 자체에는 직접 관여하지 않고, 기반 기술 인프라를 제공하는 서비스이다.
  - 메일 발송, 분산 캐시 연동, 트랜잭션 관리, 메시지 큐 통신 등이 대표적이다.
  - 환경이나 벤더 기술 변경에 유연하게 대응하기 위한 **서비스 추상화(Service Abstraction)** 의 직접적인 대상이 된다.

### 2.1. 애플리케이션 서비스

- Web Layer -> Application/Service Layer -> Infrastructure Layer로 이어지는 스프링 전형적인 3계층 아키텍처의 중심 계층에 위치한다.
- 주로 `@Service` 애노테이션을 부여하여 스프링 빈으로 등록 및 구성된다.
- 도메인 오브젝트 및 엔티티를 활용하여 핵심 애플리케이션 유스케이스 흐름을 조율한다.
- 트랜잭션, 메시징, 메일 발송 등 기반 기술을 제공하는 인프라 서비스의 지원을 받아 동작한다.
- 시스템의 가장 핵심적인 도메인 규칙 및 비즈니스 처리 흐름을 담당한다.
- 구체적인 인프라 기술이나 데이터 접근 기술에 직접 결합되지 않도록 결합도를 최소화해야 한다.
- **의존성 역전 원칙(DIP)** 을 적용하여 구체 인프라 구현체가 아닌 추상화된 인터페이스에 의존하도록 설계한다.

## 3. 추상화

- 구현의 복잡한 세부 사항은 감추고, 핵심적이고 본질적인 기능만 추출하여 단순화하는 설계 기법이다.
- 여러 인프라 서비스 기술의 공통 기능을 표준 인터페이스로 정의하고, 이를 구현하는 어댑터를 두어 기술의 변경과 무관하게 일관된 방식으로 사용할 수 있도록 지원하는 것을 **서비스 추상화(Service Abstraction)** 라고 부른다.

### 3.1. 개별 트랜잭션 기술 세부 사항에 의존하는 클라이언트

- JDBC, JPA 등 특정 트랜잭션 구현 기술에 직접 의존하면, 데이터 접근 기술을 변경할 때마다 클라이언트의 트랜잭션 제어 코드도 함께 수정되어야 한다.
- 트랜잭션 동기화 및 커밋·롤백 로직이 특정 기술에 종속되면서 코드의 복잡도가 증가하고 휴먼 에러나 버그가 발생할 위험이 커진다.
- 각 기술에서 공통으로 나타나는 트랜잭션 경계 설정 메커니즘을 추상화하여 단일 인터페이스로 규격화하고, 하위 기술이 이를 구현하도록 설계한다.
- 특정 기술이 해당 인터페이스를 직접 지원하지 않는다면 **어댑터(Adapter)** 패턴을 적용하여 연결할 수 있다.
- 스프링 프레임워크는 이를 위해 **`PlatformTransactionManager`** 라는 일관된 트랜잭션 추상화 인터페이스를 제공한다.

## 4. JdbcClient

- 스프링 6.1에 새롭게 추가된 현대적인 JDBC 데이터 접근 기술이다.
- SQL 기반의 데이터베이스 연동 코드를 유연하고 직관적인 체이닝(Fluent API) 형태로 작성할 수 있도록 지원한다.
- 내부적으로 템플릿/콜백 패턴 기반으로 동작한다.
- 기존의 전통적인 **`JdbcTemplate`을 보다 사용하기 쉽게 대체 및 보완하는 기술이다**.

### 4.1. DataSourceTransactionManager

- JDBC의 `Connection`을 활용하여 트랜잭션을 관리하는 구현체이다.
- 커넥션을 제공받기 위해 `DataSource` 오브젝트를 필수적으로 의존하며 주입받아야 한다.

## 5. 트랜잭션 프록시

- 트랜잭션 추상화를 적용해도 비즈니스 로직 내에 `TransactionTemplate`과 같은 인프라 기술 코드가 여전히 남아 관심사가 완전히 분리되지 않는다.
- 트랜잭션 경계 설정(시작·커밋·롤백)은 주로 비즈니스 메소드 실행 전후에 발생하므로, 핵심 비즈니스 로직과 기술 코드를 분리하기 위해 **프록시(Proxy)** 를 도입한다.

### 5.1. 프록시 패턴과 데코레이터 패턴

- **프록시 패턴(Proxy Pattern)**
  - 실제 대상(Target)을 대신하여 접근 제어, 지연 로딩, 보안 등의 부가적인 기능을 제공하는 패턴이다.
- **데코레이터 패턴(Decorator Pattern)**
  - 원본 오브젝트 코드를 변경하지 않고 런타임에 동적으로 새로운 책임이나 부가 기능(예: 트랜잭션 경계 설정)을 덧붙이는 패턴이다.

### 5.2. 스프링의 트랜잭션 프록시와 @Transactional

- **스프링의 트랜잭션 프록시**
  - 클라이언트와 실제 비즈니스 서비스 사이에 위치하여 트랜잭션 시작과 종료를 전담하고 비즈니스 로직만 대상 객체에 위임한다.
  - 이를 통해 비즈니스 서비스 코드는 트랜잭션 관련 인프라 코드로부터 완전히 독립된다.
- **선언적 트랜잭션 처리**
  - 스프링은 **`@Transactional`** 애노테이션이 부여된 대상에 대해 프록시 기반 AOP를 적용하여 자동으로 트랜잭션 프록시를 생성한다.
  - 비즈니스 메소드가 호출될 때 프록시가 개입하여 트랜잭션을 시작하고, 예외 발생 시 롤백하며, 정상 종료 시 커밋을 수행한다.

### 5.3. 트랜잭션 적용 검증의 중요성

- 트랜잭션이 선언된 대로 단일 단위로 바르게 동작하는지 단순 성공 케이스만으로는 판별하기 어렵다.
- 단일 트랜잭션으로 묶여 실행된 것인지, 여러 독립된 트랜잭션으로 분리 실행된 것인지 확인하기 까다롭기 때문이다.
- 따라서 비즈니스 작업 도중 강제로 예외를 발생시켜 **전체 작업이 롤백되는지 확인하는 실패 테스트 케이스**를 구축하여 원자성(Atomicity)을 검증해야 한다.
