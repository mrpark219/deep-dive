# 오브젝트와 의존관계

## 1. 오브젝트와 의존관계 기본 개념

- **스프링의 핵심 관심은 오브젝트이다**.
- 클래스와 오브젝트는 구별되는 개념이며, 자바의 오브젝트는 클래스의 인스턴스 또는 배열이다.
- **의존관계(Dependency)** 는 반드시 둘 이상의 대상이 존재하며, 한 대상이 다른 대상을 사용·호출·생성·인스턴스화·전송할 때 성립한다.
- 클래스 간에 의존관계가 존재하면 의존 대상의 변경이 이를 사용하는 클래스 코드에 영향을 준다.
- 오브젝트 사이의 의존관계는 런타임에 형성되어 실행 기능에 영향을 미치므로, **클래스 레벨의 의존관계와는 다를 수 있다**.

## 2. 관심사의 분리(Separation of Concerns)

- **관심사는 동일한 이유로 변경되는 코드의 집합이다**.
- 외부 API를 호출해 환율 정보를 가져와 JSON을 매핑하는 관심과, 결제 정보를 준비하는 비즈니스 로직의 관심은 서로 다르다.
- 변경의 이유와 시점을 면밀히 파악하여 서로 다른 관심사를 독립적으로 분리해야 한다.
- **메소드 추출(Extract Method) 리팩터링**
  - 리팩터링은 외부 동작 방식은 유지한 채 내부 구조를 개선하여 재구성하는 작업이다.
  - 리팩터링을 수행하면 코드 가독성이 향상되고 변화에 유연하게 대처할 수 있어, 개발 생산성과 소프트웨어 품질이 함께 높아진다.
  - 리팩터링이 필요한 코드의 징후를 **나쁜 냄새(Bad Smell)** 라고 부르며, 대표적인 유형인 중복 코드는 적절한 기법을 적용해 반드시 제거해야 한다.
  - 리팩터링을 효과적으로 적용하기 위해서는 체계적인 학습과 실습 훈련이 필수적이다.

## 3. 상속을 통한 확장

- 관심사를 클래스 레벨에서 분리하기 위해 **상속(Inheritance)** 을 활용할 수 있다.
- 무엇을 준비할 것인가와 데이터를 어떻게 가져올 것인가로 관심사를 분리한 뒤, 구체적인 데이터 생성 책임을 서브클래스에 위임할 수 있다.
  - 이때 객체지향 디자인 패턴 중 하나인 **팩토리 메소드 패턴**을 적용한다.
- **디자인 패턴**
  - 디자인 패턴은 소프트웨어 설계 과정에서 반복적으로 마주치는 문제를 해결하기 위해 고안된 재사용 가능한 솔루션이다.
  - 각 패턴은 명확한 이름을 가지고 있어 설계 의도와 해결 방식을 간결하게 공유할 수 있다.
  - 객체지향 설계 원칙을 기반으로 문제를 해결하며, 확장성 추구 방식은 대부분 **클래스 상속**과 **오브젝트 합성** 두 가지 구조로 귀결된다.
  - 패턴을 적용할 때는 패턴의 핵심 목적과 의도, 적용 환경, 해결할 문제와 구성 요소의 역할을 종합적으로 이해해야 한다.
- **팩토리 메소드 패턴**
  - 상속을 통해 서브클래스에서 오브젝트 생성 책임을 가지도록 기능을 확장하는 패턴이다.
  - 슈퍼클래스는 서브클래스가 구현할 메소드를 호출하여 필요한 타입의 오브젝트를 전달받아 사용한다.
  - 이때 반환 타입은 주로 인터페이스를 사용하므로 슈퍼클래스는 서브클래스가 어떤 구체 클래스를 생성해 리턴하는지 알 필요가 없다.
  - 서브클래스에서 오브젝트 생성 방식과 클래스를 결정하도록 선언해 둔 메소드를 **팩토리 메소드**라 부른다.
  - 오브젝트 생성 로직을 슈퍼클래스의 기본 흐름에서 분리하는 구조를 **팩토리 메소드 패턴**이라 한다.
  - 단순 인스턴스 생성 유틸리티 성격의 일반적인 팩토리 메소드와는 구별된다.
- **상속을 통한 확장의 한계**
  - 상속은 관심사가 다른 코드를 분리하고 독립적인 변경과 확장을 가능하게 하는 직관적인 방법이다.
  - 그러나 **상속 구조 자체의 결합도가 높다는 근본적인 한계**를 지닌다.
  - 자바는 단일 상속만 지원하므로 또 다른 관심사를 분리할 때 상속 계층을 확장하기 어렵다.
  - 상위 클래스의 변경이 하위 클래스 전반에 직접적인 영향을 미칠 수 있다.
  - **특정 목적을 가진 디자인 패턴의 적용 사례를 제외하면, 상속을 단순 관심사 분리 용도로 사용하는 것은 적절하지 않다**.
