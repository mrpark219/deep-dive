# 객체지향 설계 원칙과 패턴

## 1. 개방-폐쇄 원칙(Open-Closed Principle, OCP)

- **클래스나 모듈은 확장에는 열려 있어야 하고 변경에는 닫혀 있어야 한다**.
- 클래스가 기능을 확장할 때 기존 클래스의 코드는 변경되지 않아야 한다.

## 2. 높은 응집도와 낮은 결합도(High Cohesion and Low Coupling)

- **응집도가 높다**는 것은 하나의 모듈이 하나의 책임 또는 관심사에 집중되어 있음을 의미하며, 요구사항 변경 시 해당 모듈 내부의 수정 집중도가 높다.
- 책임과 관심사가 다른 모듈과는 **낮은 결합도**, 즉 느슨하게 연결된 관계를 유지하는 것이 바람직하다.

## 3. 전략 패턴(Strategy Pattern)

- 맥락(Context)에서 필요에 따라 변경되는 알고리즘을 인터페이스를 통해 외부로 분리하고, 이를 구현한 구체적인 알고리즘 클래스를 동적으로 교체하여 사용하는 디자인 패턴이다.
- `Collections.sort()`에 정렬 전략 오브젝트(Comparator)를 전달하여 사용하는 구조가 대표적인 사례이다.

## 4. 제어의 역전(Inversion of Control, IoC)

- **제어권 이전을 통한 제어 흐름의 역전**을 의미하며, 소프트웨어 프레임워크의 핵심 동작 원리이다.

## 5. 스프링 컨테이너와 의존관계 주입(Dependency Injection)

- **BeanFactory와 스프링 컨테이너**
  - 스프링의 **BeanFactory**는 `ObjectFactory`의 역할을 대체하며, 설정 구성 정보를 기반으로 동작한다.
  - 스프링 컨테이너는 애플리케이션을 구성하는 핵심 오브젝트인 **빈(Bean)** 을 관리한다.
- **의존관계 주입(Dependency Injection, DI)**
  - **IoC**는 프레임워크의 일반적인 동작 특성을 포괄하는 광범위한 개념이다.
  - 오브젝트 간 의존관계 설정을 외부 조립기가 전담하는 방식을 명확히 정의하기 위해 마틴 파울러(Martin Fowler)가 **의존관계 주입(DI)** 패턴이라는 용어를 제안했다.
  - 초기 스프링에서는 IoC 용어를 주로 사용했으나 점차 DI를 혼용하여 사용하게 되었으며, 기술 문서에서는 종종 **IoC/DI 컨테이너**로 표현한다.
- **컨테이너의 역할**
  - 애플리케이션 구성 오브젝트를 생성·보관하고 필요 시 제공하는 역할을 담당하는 주체를 **컨테이너**라고 부른다.
  - 컨테이너는 단순 오브젝트 보관을 넘어 빈 오브젝트의 생성, 의존관계 설정, 생명주기(Lifecycle) 관리 전반을 수행한다.
- **구성 정보(Configuration Metadata)의 정의 방식**
  - `@Configuration` 및 `@Bean` 애노테이션을 사용하는 자바 설정 클래스 방식을 통해 빈과 의존관계를 정의할 수 있다.
  - 과거에 널리 사용되던 XML 설정 파일 방식이나 생성자 파라미터 타입 기반의 자동 주입 방식을 활용할 수도 있다.
  - `@Component` 애노테이션이 부여된 클래스를 탐색하여 빈을 자동으로 등록하는 방식을 **빈 스캐닝(Bean Scanning)** 이라 하며, 이때 `@ComponentScan` 애노테이션이 사용된다.
  - 현대 스프링 애플리케이션에서는 **빈 스캐닝 방식**과 `@Configuration`/`@Bean` 기반의 **명시적 구성 정보 방식**을 상황에 맞춰 혼합하여 사용한다.

## 6. 싱글톤 레지스트리(Singleton Registry)

- **싱글톤 패턴(Singleton Pattern)**
  - GoF 디자인 패턴 중 하나로, 애플리케이션 전역에서 특정 클래스의 인스턴스가 오직 하나만 존재하도록 보장하는 패턴이다.
  - 단일 오브젝트를 전역적으로 공유해야 하는 환경에서 주로 활용된다.
  - `private` 생성자를 사용하여 상속이 불가능하다.
  - 전역 상태를 유발할 수 있어 단위 테스트 작성이 까다롭다.
  - 멀티스레드 서버 환경에서는 단일 인스턴스 생성을 엄격하게 보장하기 어렵다.
- **스프링의 싱글톤 레지스트리**
  - 스프링은 고전 싱글톤 패턴의 단점을 극복하면서 단일 오브젝트 관리 요구를 충족하기 위해 **컨테이너 레벨**에서 단일 인스턴스 유지를 보장한다.
  - 싱글톤 오브젝트를 생성하고 관리하는 스프링 컨테이너를 **싱글톤 레지스트리**라고 부른다.
- **빈 스코프(Bean Scope)**
  - 빈이 생성되고 적용되는 유효 범위를 **스코프(Scope)** 라고 정의한다.
  - 스프링의 빈은 기본적으로 싱글톤 스코프를 유지하며, 설정에 따라 프로토타입이나 웹 스코프 등 다양한 범위로 확장할 수 있다.

## 7. DI와 디자인 패턴

- 디자인 패턴은 크게 **사용 목적(Purpose)** 과 **적용 스코프(Scope)** 두 가지 기준으로 분류할 수 있다.
- 스코프 기준 분류
  - **클래스 패턴**: 상속(Inheritance)을 활용하여 구조를 확장하는 패턴이다.
  - **오브젝트 패턴**: 합성(Composition)을 활용하여 객체 간 관계를 유연하게 구성하는 패턴이다.
- 대부분의 디자인 패턴은 오브젝트 패턴에 해당하며, 객체지향 설계 원칙에서는 상속보다 오브젝트 합성을 권장한다.
- **데코레이터 패턴(Decorator Pattern)**
  - 오브젝트 코드를 수정하지 않고 런타임에 동적으로 부가 기능이나 책임을 부여하는 디자인 패턴이다.

## 8. 의존성 역전 원칙(Dependency Inversion Principle, DIP)

- 상위 수준의 모듈은 하위 수준의 모듈에 직접 의존해서는 안 되며, 두 모듈 모두 추상화(인터페이스)에 의존해야 한다.
- 추상화는 세부 구현 사항에 의존해서는 안 되며, 세부 구현 사항이 추상화에 의존해야 한다.
- 인터페이스 도입을 통한 추상화 의존뿐만 아니라 **인터페이스 소유권의 역전**까지 함께 고려해야 원칙이 완성된다.
- **분리 인터페이스(Separate Interface) 패턴**
  - 인터페이스와 구현 클래스를 서로 다른 패키지에 분리하여 배치하는 패턴이다.
  - 인터페이스를 구현체가 위치한 패키지가 아닌, 이를 호출하는 클라이언트 모듈 패키지에 함께 배치하여 의존 방향을 역전시킨다.
  - 여러 클라이언트가 인터페이스를 공유하는 경우에는 별도의 독립된 패키지로 분리하여 관리한다.
