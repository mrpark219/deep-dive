# 예외

## 1. 예외란 무엇인가

- 예외(Exception)는 프로그램의 정상적인 실행 흐름을 방해하는 비정상적인 사건을 의미한다.
- 메소드 호출 중 정상 처리가 불가능한 상황이 발생했을 때 사전에 정의된 오류 신호를 발생시키는 메커니즘이다.
- **사용 원칙:**
  - 예외는 오직 예외적인 상황에서만 사용해야 하며, 흐름 제어(반복문 탈출 등) 목적으로 남용해서는 안 된다.
  - 빈번한 예외 발생은 코드 설계상의 결함이나 버그를 의미할 가능성이 높다.

## 2. 예외 발생 시 판단 기준

- 예외를 잡았을 때(catch) 무조건적인 처리보다 다음 단계에 따른 순차적 판단이 요구된다.
- **복구 가능한 예외 판단**
  - 정상 흐름으로 복구 가능한지 확인한다.
  - 일시적 네트워크 지연에 대한 재시도(Retry)나 대체 서버로 요청을 돌리는 페일오버(Failover) 등을 검토한다.
- **버그 여부 판단**
  - 복구가 불가능한 경우 시스템 내부 버그인지 확인한다.
  - `NullPointerException`, `IndexOutOfBoundsException` 등 자체 로직 오류인지 점검한다.
  - `IllegalArgumentException`처럼 클라이언트의 잘못된 파라미터 전달로 인한 호출자 결함인지 확인한다.
  - 버그는 복구 대상이 아니므로 빠른 발견과 원인 수정을 목표로 하며, 로깅 후 알림 전송이나 프로세스 종료 등으로 대응한다.
- **제어 불가 상황 판단**
  - 디스크 공간 부족, 서버 다운, `OutOfMemoryError` 등 애플리케이션 레벨에서 대응할 수 없는 외부 요인은 인프라 및 시스템 차원(로깅, 알림, 프로세스 재기동)에서 처리한다.

## 3. 예외 처리의 대표적인 안티패턴

### 3.1. 예외 무시

```java
try {
    // ...
} catch (Exception e) {
    // 아무것도 하지 않음
}
```

- 발생한 예외를 은폐하여 디버깅을 불가능하게 만들고 시스템 장애의 원인을 찾기 어렵게 만든다.

### 3.2. 단순 콘솔 출력 후 방치

```java
try {
    // ...
} catch (Exception e) {
    e.printStackTrace();
}
```

- 예외 상황에 대한 실질적인 복구, 알림, 로깅 프레임워크 연동이 누락되어 사실상 예외 무시와 동일하다.
- 운영 서버 환경에서는 표준 출력 로그가 유실되기 쉬워 장애 인지가 늦어진다.

### 3.3. 무의미하고 무책임한 throws

```java
public void method1() throws Exception {
    method2();
}

public void method2() throws Exception {
    method3();
}

public void method3() throws Exception {
    // ...
}
```

- 최상위 타입인 `Exception`을 무차별적으로 던지면 호출자가 구체적인 예외 유형을 파악할 수 없다.
- 호출부에서도 포괄적인 `catch (Exception e)` 처리를 남발하게 만들어 예외 은폐 패턴을 유발한다.

## 4. 예외의 종류

- 자바의 예외 계층 구조는 크게 세 가지로 분류된다.

| 종류                         | 상속 관계                              | 체크 여부  |
| ---------------------------- | -------------------------------------- | ---------- |
| Error                        | Throwable 직속                         | 체크 안 함 |
| Exception (checked)          | Exception 상속 (RuntimeException 제외) | 체크함     |
| RuntimeException (unchecked) | RuntimeException 상속                  | 체크 안 함 |

## 5. Error

- 시스템 레벨에서 심각한 비정상 상태가 발생했을 때 JVM이 던진다.
- 복구가 불가능하거나 무의미하므로 애플리케이션 레벨에서 catch하여 복구를 시도해서는 안 된다.
- 대표적인 예시로는 메모리가 고갈된 `OutOfMemoryError`, 스레드 강제 종료 시 발생하는 `ThreadDeath`, 과도한 재귀 호출로 인한 `StackOverflowError`가 있다.

## 6. 체크 예외(Checked Exception)

- `Exception`을 상속하되 `RuntimeException`을 상속하지 않는 예외 유형이다.
- 컴파일러가 try-catch 처리나 메소드 시그니처의 throws 선언을 강제한다.
- **문제점:**
  - 자바 초기 API(대표적으로 JDBC) 설계 관행에서 체크 예외가 과도하게 사용되었다.
  - `SQLException`처럼 실제 복구 불가능한 인프라 예외까지 체크 예외로 지정되어, 호출 계층마다 강제 catch나 throws 선언을 유발했다.
  - 결과적으로 무책임한 throws 선언이나 catch 블록 내 예외 무시 같은 안티패턴을 초래했다.
- **권장 사항:**
  - 복구 불가능한 체크 예외를 접했을 때는 무의미한 상위 전파를 지양한다.
  - **런타임 예외(RuntimeException)로 포장(Wrapping)** 하여 던지거나 비즈니스 계층에 맞는 의미 있는 예외로 변환한다.
  - 이를 통해 불필요한 throws 선언이 상위 아키텍처 계층으로 누수되는 것을 차단한다.

## 7. 예외의 추상화와 전환

- **문제 상황**
  - 동일한 도메인 관점의 오류(예: 데이터 조회 실패)라도 하위 기술 스택에 따라 발생하는 예외가 달라진다.
  - 순수 JDBC 사용 시 `SQLException`이 발생하며 JPA 사용 시 `PersistenceException` 계열이 발생한다.
- **예외 추상화**
  - 하위 기술에 종속적인 예외를 상위 비즈니스 계층에 노출하지 않고, 기술 독립적인 공통 예외(예: 스프링의 `DataAccessException`)로 추상화하여 전달한다.
- **예외 전환(Translation)**
  - catch한 하위 예외를 도메인이나 계층에 적합한 새로운 예외 객체로 감싸서(Chaining) 다시 던지는 기법이다.
  - 상위 계층이 구체적인 데이터 접근 기술을 알 필요가 없어 느슨한 결합도를 유지할 수 있다.
  - 구현 기술이 변경되어도 상위 비즈니스 코드에 수정이 발생하지 않는다.
  - 원본 원인 예외(`cause`)를 보존하여 스택 트레이스 추적 및 디버깅을 지원한다.
- **설계 원칙**
  - 예외는 발생 원인뿐만 아니라 처리되는 아키텍처 계층과 도메인 맥락의 의미를 함께 고려하여 설계해야 한다.
