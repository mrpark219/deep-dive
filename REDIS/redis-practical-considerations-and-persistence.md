# Redis 주의 사항 & Memory Persistence

## 1. Key 관리 기법과 주의 사항

### 1.1. KEYS 명령어

- `KEYS <Pattern>` 형태로 사용하며, 지정한 **패턴에 매칭되는 모든 키**를 반환하는 명령어이다.
- 글로브(Glob) 스타일의 패턴 매칭을 지원하며, 다음과 같은 와일드카드를 사용할 수 있다.
  - `*`: 모든 문자열과 매칭되는 와일드카드이다. (예: `KEYS *`는 데이터베이스의 **모든 키**를 반환한다.)
  - `user:*`: `user:`로 시작하는 모든 키와 매칭된다. (예: `user:a`, `user:b`, `user:test:1` 등)
  - `[...]`: 특정 **문자 집합**과 매칭된다. (예: `KEYS user:[123]*`는 `user:1`, `user:2`, `user:3`처럼 대괄호 안에 나열된 문자로 시작하는 키와 매칭된다.)
  - `[a-z]`: 문자 **범위**를 지정할 수도 있다. (예: `KEYS user:[a-z]*`는 `user:` 뒤에 소문자 알파벳이 오는 키와 매칭된다.)
  - `\*`: 백슬래시로 이스케이프하면 `*`는 와일드카드가 아닌 **일반 문자**로 취급되어, `user:*`라는 리터럴 문자열을 가진 키만 찾는다. (예: `KEYS user:\*`)
- **KEYS의 치명적인 단점**
  - 실행되는 동안 **서버 전체를 블로킹**하며, 시간 복잡도는 $O(N)$이다. (N은 데이터베이스 전체 키 개수)
  - Redis는 모든 키를 순회하면서 패턴과 비교하기 때문에, 키가 100만 개라면 100만 번의 비교 연산이 발생한다.
  - Redis는 **싱글 스레드**로 동작하므로, KEYS 명령어가 실행되는 동안에는 다른 모든 명령어가 대기해야 하며, 이 시간은 몇 초에서 몇십 초까지 걸릴 수도 있다.

- **결론적으로 KEYS는 프로덕션 환경에서 절대 사용해서는 안 된다.**
  - 개발 환경이나 로컬 테스트, 혹은 기능 구현 단계에서 편의상 데이터를 확인할 때만 제한적으로 사용하는 명령어이다.

### 1.2. SCAN 명령어

- KEYS의 완벽한 대안으로, `SCAN <Cursor> [MATCH Pattern] [COUNT Count] [TYPE Type]` 형태로 사용한다.
- **커서(Cursor) 기반**으로 키를 일부씩 나누어 반환하는 방식으로 동작한다.
- 최초 호출 시에는 커서 값을 **0**으로 시작한다.
- 반환값은 항상 **두 개의 요소로 구성된 배열**이다.
  - 첫 번째 요소: 다음 호출에 사용할 **다음 커서(Next Cursor)** 값
  - 두 번째 요소: 이번 커서에서 반환된 **키 배열**
- **동작 예시:**
  - `SCAN 0`을 실행하면 `17, [키1, 키2, 키3]`과 같은 형태로 결과가 반환된다고 가정한다.
  - 여기서 `17`은 다음 호출에 사용할 커서이고, 나머지는 이번에 반환된 키들이다.
  - 다음 호출은 `SCAN 17`이 되며, 이 과정을 반복하다가 **커서가 다시 0으로 돌아오면 전체 순회가 완료**된 것이다.
  - 즉, 커서 `0`은 순회의 **시작과 끝**을 동시에 의미한다.
- **성능 특성:**
  - 각 호출은 **COUNT 값에 비례하는 시간 복잡도**를 가지며, COUNT는 보통 작은 상수 값이므로 개별 호출은 빠르게 완료된다.
  - SCAN도 서버를 블로킹하기는 하지만, **전체 데이터를 한 번에 가져오지 않고 필요한 만큼 나누어 호출**하기 때문에 각 호출 사이에 다른 명령어가 처리될 수 있는 여지가 생긴다.
  - 키가 100만 개가 있어도 한 번에 소량씩만 처리하므로 KEYS보다 훨씬 안전하다.
- **주의할 점: 중복 반환 가능성**
  - 순회 도중 키가 추가되거나 삭제될 수 있고, Redis 내부 해시 테이블이 리사이징되며 키의 위치가 바뀔 수도 있어 **동일한 키가 여러 번 반환될 가능성**이 있다.
  - 따라서 SCAN을 사용할 때는 **애플리케이션 단에서 중복 처리 로직**을 함께 구현해 주는 것이 좋다.
- **보장 사항:**
  - 순회를 시작할 때 이미 존재하던 키는, 순회 도중 삭제되지 않는 한 **반드시 최소 한 번은 반환됨을 보장**한다.
  - 다만 순회 도중 **새로 추가된 키**는 반환될 수도, 반환되지 않을 수도 있다.

### 1.3. EXISTS 명령어

- `EXISTS <Key> [Key ...]` 형태로 사용하며, 지정한 **키의 존재 여부**만을 확인하는 명령어이다.
- 키가 존재하면 **1**, 존재하지 않으면 **0**을 반환한다. (예: `EXISTS user:1000`)
- Redis 3.0.3 버전부터는 **여러 개의 키를 한 번에 확인**할 수 있으며, 이 경우 **존재하는 키의 개수**를 반환한다.
  - 예: `EXISTS user:1000 user:2000`을 실행했을 때 둘 다 존재하면 2, 하나만 존재하면 1을 반환한다.
- 동일한 키를 여러 번 지정하면 **중복으로 카운트**된다. (예: `EXISTS myKey myKey myKey`에서 myKey가 존재한다면 3이 반환된다.)
- **활용 시 유의점**
  - 값 없이 키의 존재 여부만 확인하고 싶을 때 대표적으로 사용된다.
  - `GET`을 사용해 값을 가져온 뒤 `nil` 여부로 존재를 판단할 수도 있지만, **EXISTS를 사용하는 것이 의도상 훨씬 명확**하다.
  - List, Set, Hash와 같이 **String이 아닌 타입의 키**는 `GET` 명령어로 조회할 경우 에러가 발생하지만, `EXISTS`는 타입에 관계없이 항상 정상적으로 동작한다.
  - 다만 String 타입의 키에서 **값 자체도 필요한 경우**에는 처음부터 `GET`을 호출하는 것이 효율적이다.
  - 순수하게 **존재 여부만 확인**하는 경우라면 `EXISTS`를 사용하는 것이 좋다. `GET`으로 값 전체를 가져오는 것은 네트워크 자원을 낭비하는 반면, `EXISTS`는 0과 1로 이루어진 최소한의 데이터만 주고받기 때문에 네트워크 관점에서 훨씬 효율적이다.

### 1.4. 그 밖의 Key 관련 명령어

- 이 외에도 Redis에는 다음과 같은 다양한 키 관련 명령어가 존재한다.
  - **RANDOMKEY**: 데이터베이스에서 임의의 키 하나를 무작위로 반환한다.
  - **TYPE**: 지정한 키의 데이터 타입을 확인한다.
  - **RENAME**: 키의 이름을 변경한다.

## 2. 데이터 영속성 (Persistence) 3가지 패턴

### 2.1. 영속성이 필요한 이유

- Redis의 가장 큰 특징은 **모든 데이터를 메모리(RAM)에 저장**한다는 점이며, 디스크가 아닌 램에 데이터가 위치하기 때문에 **마이크로초($\mu s$) 단위의 빠른 응답**을 제공한다.
- 하지만 메모리는 전원이 꺼지면 저장된 데이터가 모두 사라지는 **휘발성**이라는 근본적인 한계가 존재한다.
- 보안 패치, 기능 배포, Redis 자체 업그레이드 등 **운영 중 불가피한 서버 재시작**이나, 하드웨어·네트워크 장애 등 **예기치 못한 장애** 발생 시 메모리의 데이터가 완전히 초기화될 수 있다.
- **영속성(Persistence)** 은 이러한 문제를 해결하기 위해 메모리의 데이터를 디스크에 주기적 또는 실시간으로 기록하여, 서버 재시작 후에도 이전 상태로 **복구(Restore)** 할 수 있도록 보장하는 기능이다.

### 2.2. 영속성의 필요 여부 판단

- **영속성이 불필요한 경우**: 단순 캐시(Cache) 용도로 사용하는 경우가 대표적이다.
  - 원본 데이터가 RDBMS 등에 이미 존재하고 Redis는 조회 속도 향상을 위한 **임시 복사본**만 유지하는 경우이다.
  - 데이터가 사라져도 DB에서 다시 읽어와 재캐싱할 수 있으므로, 잠시 성능이 하락할 뿐 **치명적인 데이터 손실로 이어지지 않는다**.
- **영속성이 필요한 경우**: 세션 관리, 장바구니, 진행 상태 등 Redis에만 저장되는 데이터를 다루는 경우이다.
  - 데이터 유실 시 **사용자 경험(UX)이 심각하게 저하**되거나 결제·포인트 등 **비즈니스 핵심 데이터의 손실**이 발생하므로 영속성 설정이 필수적이다.
- Redis는 **RDB**, **AOF**, **하이브리드(Hybrid)** 3가지 영속성 패턴을 제공한다.

### 2.3. RDB (Redis Database) 방식

- 특정 시점의 메모리 전체 상태를 하나의 파일로 기록하는 **스냅샷(Snapshot) 방식**이다.
- 바이너리(Binary) 형식 파일인 **`dump.rdb`** 로 저장되며 압축이 진행되므로 **파일 크기가 작고 로딩 속도가 빠르다**.

#### 동작 방식

- **백그라운드 포크(Fork)**: `BGSAVE` 명령 시 `fork()` 시스템 콜을 호출하여 **자식 프로세스**를 생성한다.
- **Copy-On-Write (COW)**:
  - 포크 직후 부모 프로세스와 자식 프로세스는 **동일한 메모리 페이지를 공유**한다.
  - 자식 프로세스는 공유 메모리를 순회하며 디스크에 바이너리 파일로 저장한다.
  - 저장 동안 부모 프로세스가 데이터를 변경할 경우, **해당 메모리 페이지만 따로 복사**하여 수정하므로 메인 스레드의 서비스 요청 처리를 방해하지 않는다.
- **주기적 조건 저장**: 설정된 시간 및 변경 횟수 조건에 맞춰 스냅샷이 생성된다. (예: 15분 동안 1회 이상 변경 시)

#### 장단점

- **장점**: 단일 파일 형태로 **백업 및 이동이 용이**하며, 바이너리 로딩 방식으로 **복구 속도가 매우 빠르다**.
- **단점**:
  - 스냅샷 주기 사이에 장애가 발생하면 **마지막 스냅샷 이후의 데이터가 완전히 유실**된다.
  - COW 특성상 부모 프로세스의 쓰기 요청이 대량으로 발생할 경우 **최악의 경우 메모리 사용량이 2배까지 증가**할 수 있다.
  - 대용량 메모리 환경에서는 `fork()` 수행 순간 순간적인 **메모리 복제 지연(Stall)** 및 **디스크 I/O 부하**가 발생한다.
  - 바이너리 파일임으로 사람이 읽거나 수정할 수 없다.

### 2.4. AOF (Append Only File) 방식

- 데이터 변경을 유발하는 모든 쓰기 명령(`SET`, `DEL` 등)을 로그 파일에 **순차적으로 기록(Append)** 하는 방식이다.
- 서버 재시작 시 AOF 파일에 기록된 모든 명령을 처음부터 순서대로 재실행하여 메모리를 **장애 직전 상태로 복구**한다.

#### 디스크 동기화 (fsync) 전략

- **`always`**: 매 쓰기 명령어마다 즉시 디스크 동기화를 수행한다. 데이터 안전성은 극대화되나 **디스크 I/O 병목으로 성능이 크게 저하**된다.
- **`everysec` (기본 권장값)**: 1초마다 OS 버퍼의 데이터를 디스크에 저장한다. 성능과 데이터 안전성 간의 **가장 이상적인 균형**을 제공한다. (최대 1초 분량 유실 가능)
- **`no`**: 디스크 저장 시점을 운영체제(OS)의 커널에 위임한다. (성능은 높으나 데이터 손실 가능성 증가)

#### AOF 재작성 (Rewrite)

- 로그가 지속적으로 쌓여 파일 크기가 지나치게 커지는 문제를 방지하는 기능이다.
- 현재 메모리 상태를 기준하여 **동일한 키의 중복 명령을 하나로 축소**한 최적화된 새로운 AOF 파일을 백그라운드에서 다시 생성한다.

#### 장단점

- **장점**:
  - `everysec` 설정 시 **데이터 손실을 최대 1초 이내로 최소화**할 수 있다.
  - 텍스트 파일 구조이므로 실수로 실행한 `FLUSHALL` 명령을 파일 편집으로 삭제하여 **손쉽게 원상 복구**할 수 있다.
- **단점**:
  - 바이너리 파일에 비해 **파일 크기가 크다**.
  - 저장된 모든 명령을 하나씩 순차 재실행하며 복구해야 하므로 **RDB에 비해 복구 속도가 느리다**.

### 2.5. 하이브리드 (Hybrid) 방식

- **Redis 4.0**부터 도입되었으며 RDB의 빠른 복구 능력과 AOF의 높은 데이터 안전성을 결합한 **권장 방식**이다.
- 단일 AOF 파일 내에 **앞부분은 RDB 스냅샷(바이너리)** 으로, **뒷부분은 AOF 명령어(텍스트 로그)** 로 혼합 구성한다.

#### 동작 방식 및 복구 과정

1. **AOF 재작성(Rewrite) 시점**: 현재 메모리 전체 상태를 **RDB 바이너리 형태**로 AOF 파일 앞부분에 우선 기록한다.
2. **재작성 중 추가 변경분**: 재작성이 진행되는 동안 들어온 쓰기 명령어는 파일 뒷부분에 **AOF 텍스트 형태**로 추가 기록한다.
3. **복구 진행**:
   - 파일 앞부분의 RDB 스냅샷을 빠르게 메모리에 로드한다. ($O(1)$에 가까운 대용량 빠른 복구)
   - 이후 뒷부분에 남아있는 최소한의 AOF 명령어만 차례로 재실행하여 **빠르고 완벽하게 복구**를 완료한다.

#### 장단점

- **장점**: **복구 속도가 매우 빠르며** 데이터 유실 역시 **최대 1초 수준으로 최소화**된다.
- **단점**: 단일 파일 내에 바이너리와 텍스트 포맷이 섞여 있어 사람이 직접 텍스트 에디터로 파일을 수정하기 어렵다.
