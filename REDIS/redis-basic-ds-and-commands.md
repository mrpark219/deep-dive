# Redis 기본 자료 구조와 명령어

## 1. String 타입

- 가장 기본적인 형태이자 가장 널리 사용되는 데이터 타입이다.
- 이름은 String이지만 실제로는 **바이트 배열(Byte Array)** 로 구현되어 있다.
- 단순 텍스트뿐만 아니라 숫자, 이진 데이터, 직렬화된 JSON 객체 등 다양한 형태의 데이터를 저장할 수 있다.
- Redis의 모든 키(Key)는 기본적으로 String 타입이다. 즉, 키와 값 모두 String으로 구성될 수 있다.

### 1.1. 바이너리 세이프 (Binary Safe)

- 일반적인 C 언어의 문자열은 문자열의 끝을 나타내기 위해 널 종료 문자(`Null byte`, `\0`)를 사용한다.
- 이 때문에 문자열 중간에 널 바이트가 포함되면 데이터가 잘리는 문제가 발생하여, 이미지나 압축 파일 같은 이진 데이터는 일반 문자열로 저장하기 어렵다.
- 하지만 Redis String은 이러한 제약이 없는 **바이너리 세이프(Binary Safe)** 구조이다.
- Redis는 널 바이트 대신 **문자열의 길이를 별도로 저장하고 관리**하므로 널 바이트를 포함한 모든 바이트 값을 온전히 저장할 수 있다.
- 따라서 텍스트뿐만 아니라 JPG, PDF 파일 또는 직렬화된 프로토콜 버퍼(Protocol Buffers) 데이터 등 **모든 이진 데이터**를 저장할 수 있다.

### 1.2. 크기 제한 및 권장 사항

- String 타입의 최대 크기는 **512MB**이다.
- 이론적으로 약 5억 3천만 글자를 저장할 수 있다.
- 하지만 성능 유지를 위해 작은 값으로 쪼개어 저장하는 것이 권장된다.
- Redis는 모든 데이터를 메모리에 저장하므로, 하나의 키에 100MB 크기의 데이터를 저장하면 조회할 때마다 100MB를 네트워크로 전송해야 한다.
- 이로 인해 **네트워크 대역폭이 낭비**되고 다른 요청 처리가 지연될 수 있다.
- 따라서 스트링 값은 수 바이트에서 킬로바이트(KB) 단위로 가볍게 다루는 것이 적합하다.
- 대용량 데이터를 다뤄야 할 경우 데이터를 여러 조각으로 나눌 수 있는지 검토하는 등 **트레이드오프(Trade-off)** 를 고려해야 한다.

## 2. SDS (Simple Dynamic String)

- Redis는 기본적으로 C 언어로 작성되어 있다.
- 하지만 C 언어의 기본 문자열 구조를 사용하지 않고, **SDS(Simple Dynamic String)** 라는 자체 문자열 구조를 사용한다.

### 2.1. SDS 구성요소

- **len (int)**: 실제 저장된 문자열의 길이
- **free (int)**: 할당되어 있는 여유 공간의 크기
- **buf (char[])**: 실제 문자 데이터가 저장되는 바이트 배열

### 2.2. SDS를 사용하는 이유

- **O(1) 시간 복잡도의 문자열 길이 조회**: C 언어 기본 문자열은 길이를 측정하려면 전체를 순회해야 하지만, SDS는 `len` 필드를 참조하여 즉시 확인할 수 있다.
- **버퍼 오버플로우 방지**: 문자열 추가 시 `len`과 `free` 필드를 미리 확인하여 오버플로우를 방지하고 안전하게 메모리를 관리한다.
- **바이너리 세이프 (Binary Safe)**: 널 문자(`\0`)가 아닌 `len` 값을 기준으로 문자열의 끝을 판단하므로 임의의 이진 데이터를 안전하게 저장할 수 있다.
- **효율적인 Append 연산**: `free` 공간이 남아있다면 메모리 재할당 없이 즉시 문자열을 추가한다. 재할당이 필요한 경우에도 여유 공간을 미리 확보하여 이후 추가 연산 속도를 높인다.

### 2.3. SDS 3가지 인코딩 방식

- 데이터 종류와 크기에 따라 메모리 사용을 최적화하기 위해 3가지 인코딩 방식을 지원한다.
  - **int**: Redis 객체 헤더(16바이트) + 정수값(8바이트) = 약 24바이트
  - **embstr**: Redis 객체와 SDS를 합쳐서 연속 배치 = 약 20바이트 + 문자열 길이
  - **raw**: Redis 객체(16바이트) + SDS 헤더(8바이트) + 문자열 길이 + 여유 공간

#### int 인코딩

- 정수로 표현 가능한 숫자 데이터일 때 사용한다.
- 저장할 값이 `long` 타입 범위($-2^{63}$ ~ $2^{63} - 1$) 내의 정수라면 문자열이 아닌 **정수형 값**으로 직접 저장한다.

#### embstr 인코딩

- **44바이트 이하**의 짧은 문자열에 사용된다.
- Redis 객체 헤더(16바이트)와 SDS 헤더, 실제 데이터를 **하나의 연속된 메모리 블록**으로 함께 할당한다.
- 메모리 할당 및 해제가 한 번만 이루어져 생성 속도가 빠르고 **메모리 단편화를 줄여준다**.
- 데이터가 연속 배치되므로 **CPU 캐시 히트율(Cache Hit Ratio)** 이 향상된다.
- 44바이트 기준은 메모리 할당자(jemalloc 등)의 기본 단위인 64바이트 내에 객체 헤더와 SDS 헤더, 데이터를 모두 담기 위한 설정이다.
- **읽기 전용(Read-Only)** 으로 동작하며, 데이터 수정이 발생하면 `raw` 인코딩으로 자동 변환된다.

#### raw 인코딩

- **44바이트를 초과**하는 긴 문자열을 처리하는 기본 방식이다.
- Redis 객체 헤더와 SDS 구조가 **서로 다른 메모리 영역**에 분리되어 관리되며, 객체 포인터가 SDS를 가리킨다.
- 문자열 수정 시 메모리 재할당 및 확장이 용이하여 동적 변경이나 반복적인 **Append 연산에 매우 유연**하게 대응한다.

## 3. Redis 기본 명령어

### 3.1. SET

- 데이터를 저장할 때 사용하는 가장 기본적인 명령어이다.
- `SET <Key> <Value>` 형태로 키와 값을 함께 저장한다.
- 저장하려는 키가 이미 존재할 경우 **기존 값을 덮어쓴다**.
- 덮어쓸 때는 기존 값의 **데이터 타입이 달라도 상관없이** 새로운 String 값으로 변경된다.

#### Key Naming 규칙

- 콜론(`:`)을 구분자로 활용하여 데이터의 **계층적 구조**를 표현한다.
  - 예: 사용자 이름 저장 시 `user:1000:name`
- 키 이름에는 **공백을 사용하지 않고**, 구분 단어로 언더바(`_`) 등을 활용한다.
- 키 이름이 지나치게 길어지면 메모리가 낭비되므로 적절한 길이를 유지한다.
- 규칙적인 키 네이밍은 운영 및 디버깅 시 가독성을 높여준다.
- **Redis Insight**와 같은 GUI 모니터링 도구에서는 콜론(`:`) 규칙을 기반으로 키를 **폴더 형태의 계층 구조 UI**로 시각화해 준다.

### 3.2. GET

- 지정한 키에 저장된 값을 조회할 때 사용한다.
- `GET <Key>` 형태로 입력하며, 저장된 값을 즉시 반환한다.
- 조회하려는 키가 존재하지 않을 경우 **`nil`** 을 반환하며,이는 Redis에서 값이 없음을 의미한다.
- **String 타입 전용 명령어**이므로 조회 전 데이터 타입을 확인해야 한다. List, Set, Hash 등 다른 자료구조에 실행 시 **에러가 발생**한다.
- 반환된 문자열 데이터는 애플리케이션 영역에서 가져와 **특정 객체나 클래스로 역직렬화(Deserialization)** 하여 사용하는 것이 일반적이다.

## 4. 카운터 명령어

### 4.1. 단일 단위 카운터 (INCR, DECR)

- **`INCR` (Increment)**: 지정한 키의 숫자를 **1 증가**시키는 명령어이다.
- **`DECR` (Decrement)**: 지정한 키의 숫자를 **1 감소**시키는 명령어이다.
- 존재하지 않는 키에 실행하면 값을 먼저 **0으로 자동 초기화**한 후 연산을 수행하므로 사전 초기화 작업이 필요 없다.
- 저장된 값이 정수로 변환될 수 없는 문자열 형태라면 명령어 처리가 거부되고 **에러가 발생**한다.

### 4.2. 원자성 (Atomicity) 및 경쟁 상태 방지

- 카운터 관련 명령어는 모두 **원자적(Atomic) 연산**으로 동작한다.
- 일반적인 카운트 증가는 데이터를 읽고, 1을 더하고, 다시 저장하는 3단계를 거치지만 Redis는 이를 **단일 명령으로 처리**한다.
- 연산 중간에 다른 클라이언트 요청이 개입할 수 없으므로, 애플리케이션에서 직접 값을 다룰 때 발생하는 **경쟁 상태(Race Condition)** 를 완벽히 방지한다.

### 4.3. 다중 단위 카운터 (INCRBY, DECRBY)

- **`INCRBY` / `DECRBY`**: 1씩 변경하는 기본 명령어와 달리, 지정한 숫자(`By` 뒤의 입력값)만큼 **가중치를 두어 증가 및 감소**시킨다.
- 단일 단위 명령어와 동일하게 **원자적 연산**을 보장한다.

## 5. 다중 작업 명령어

### 5.1. 다중 저장을 위한 MSET

- **`MSET` (Multi SET)**: 여러 개의 키-값(Key-Value) 쌍을 단 한 번의 요청으로 저장하는 명령어이다.
- **네트워크 RTT(Round Trip Time) 단축**:
  - Redis 자체 연산 속도가 아무리 빨라도 네트워크 왕복 시간(RTT)은 물리적 지연을 발생시킨다.
  - 예를 들어 RTT가 1ms일 때 `SET` 명령어를 10번 개별 전송하면 최소 10ms가 소요된다.
  - `MSET`을 활용하면 10개의 데이터를 단 1회의 네트워크 왕복만으로 처리하여 지연 시간을 획기적으로 줄일 수 있다.
- **사용법**: `MSET key1 value1 key2 value2 ...` 형태로 키와 값을 번갈아 나열한다.
  - 예: `MSET user:1000:name "김철수" user:1000:email "test@test.com"`
- **원자성 보장**: 모든 키가 성공적으로 저장되거나 완전히 실패하는 All-or-Nothing 원자적 연산을 보장한다. (중간 부분 성공 없음)
- **적정 전송량 유지**: Redis는 **단일 스레드**로 동작하므로 `MSET` 처리 동안 다른 요청이 대기해야 한다. 따라서 한 번에 너무 많은 데이터를 담지 않고 **10~100개 단위**로 분할 실행하는 것이 바람직하다.

### 5.2. 다중 조회를 위한 MGET

- **`MGET` (Multi GET)**: 여러 개의 키에 해당하는 값을 한 번에 조회하는 명령어이다.
- **응답 방식**: 입력한 키의 순서대로 값을 배열 형태로 반환한다.
- 존재하지 않는 키가 포함된 경우 해당 위치에 **`nil`** 을 응답한다.
- `MSET`과 동일하게 **단일 원자적 명령어**로 동작하여 처리 효율을 극대화한다.

### 5.3. `MSET`/`MGET`과 파이프라이닝(Pipelining)의 차이

- **파이프라이닝 (Pipelining)**:
  - 서로 다른 다양한 명령어(`SET`, `GET`, `INCR` 등)를 하나의 네트워크 패킷으로 묶어 순차 실행하는 기법이다.
  - 단일 명령어가 아닌 복수 명령어의 모음이므로 **원자성을 보장하지 않는다**.
  - 실행 중간에 다른 클라이언트의 요청이 개입할 수 있어 경쟁 상태가 발생할 수 있다.
- **`MSET` / `MGET`**:
  - 그 자체로 **하나의 단일 명령어**로 실행된다.
  - 연산이 끝날 때까지 다른 클라이언트 요청이 개입할 수 없어 **완벽한 원자성을 보장**한다.

## 6. SET 명령어 옵션

- **데이터 만료 (TTL, Time To Live)**: 캐시 데이터의 유지 기간을 지정하여 만료 시 자동으로 삭제되도록 설정할 수 있다.
- Redis의 메모리는 제한적이므로 오래된 데이터를 자동 삭제하고 데이터 유효 기간을 관리하거나 세션 정보를 제어할 때 필수적이다.
- **`SETEX`**: `SET`과 `EXPIRE`를 합친 과거 명령어로, 지정한 초 단위 시간 후 키를 자동 만료시킨다. (예: `SETEX sessions:abcd1234 3600 "session_data"`)
- 최신 Redis에서는 일반 `SET` 명령어에 `EX` 옵션을 추가하는 방식을 권장하므로 `SETEX` 단독 명령어는 잘 사용하지 않는다.

### 6.1. `SET NX` 옵션

- **`NX` (Not Exists)**: 대상 키가 **존재하지 않을 때만** 값을 저장하는 옵션이다.
- 키가 이미 존재할 경우 아무 작업도 수행하지 않고 실패를 반환한다.
- 관계형 데이터베이스(RDB)의 `INSERT IGNORE` 구문과 유사하게 동작한다.
- 일반 `SET`이 기존 데이터를 덮어쓰는 것과 달리, **중복 방지** 및 **데이터 오버라이드 예방** 목적으로 활용된다.
- 여러 서버 환경에서 동시성을 제어하는 **분산 락(Distributed Lock)** 구현의 핵심 기법으로 사용된다.

## 7. List 타입

- Redis의 List는 **문자열 값들의 연결 리스트(Linked List)** 구조이다.
- 일반적인 배열(Array)과 달리 Head(맨 앞)와 Tail(맨 뒤) 양쪽 끝에서 요소를 추가하거나 제거하는 작업이 매우 빠르다.
- 리스트 양 끝단에서의 삽입 및 삭제 연산은 요소 개수와 무관하게 **$O(1)$의 시간 복잡도**를 보장한다.

### 7.1. 내부 구현 및 인코딩 구조

- **Redis 3.2 이전**: 리스트 크기에 따라 인코딩이 분기된다.
  - **ziplist**: 요소 개수가 적고 크기가 작은 경우 메모리 절약을 위한 연속 배열 구조
  - **linkedlist**: 요소가 많거나 크기가 큰 경우 사용하는 일반 연결 리스트 구조. 요소 하나하나가 이전 및 다음 요소의 메모리 주소를 가리키는 포인터로 연결된다.
- **Redis 3.2 이후**: **quicklist** 구조가 도입되어 위 두 방식이 하나로 통합된다.
  - 전체 리스트를 여러 개의 작은 노드로 나누고, 각 노드 내부는 압축 배열(ziplist 또는 listpack)로 저장하여 메모리 효율을 확보한다.
  - 노드와 노드 사이는 이중 연결 리스트로 연결되어 양 끝단에서의 빠른 삽입·삭제 성능을 유지한다.
  - 포인터 체이닝은 요소 단위가 아니라 **노드 단위**에서 일어난다. 노드에 여유가 있으면 배열 안에 데이터를 채워 넣고, 노드가 꽉 찼을 때만 새 노드를 만들어 포인터로 연결한다.
- **Redis 7.0 이후**: quicklist 노드의 내부 인코딩이 `ziplist`에서 `listpack`으로 교체된다.
  - ziplist는 이전 요소의 길이 정보를 함께 저장하는 방식 때문에 요소 삽입·삭제 시 연쇄적으로 재계산이 일어나는 cascade update 문제가 있었다.
  - listpack은 이 문제를 해결한 개선된 인코딩이다.
  - 리스트가 매우 작으면 quicklist로 감싸지 않고 listpack 단일 구조만 사용하다가, 임계값(기본 8KB, `list-max-listpack-size`)을 넘으면 quicklist로 전환된다.

### 7.2. 주요 특징 및 한계

- 저장 가능한 최대 요소 수: **$2^{32} - 1$개** (약 42억 개, 실제 한계는 서버의 가용 RAM 용량에 따름)
- **중복 허용**: Set과 달리 동일한 값의 중복 저장을 허용한다.
- **인덱스 접근**: 포인터를 추적하여 필요시 특정 인덱스 기반의 접근도 지원한다.

### 7.3. 주요 명령어

#### 데이터 추가 (`LPUSH`, `RPUSH`)

- **`LPUSH`**: 리스트의 Head(맨 앞)에 하나 이상의 요소를 추가하고, 연산 후 **리스트의 전체 길이**를 반환한다.
  - 예: `LPUSH key value1 value2` 실행 시 `value2`, `value1` 순으로 저장된다.
- **`RPUSH`**: 리스트의 Tail(맨 뒤)에 하나 이상의 요소를 추가하고 전체 길이를 반환한다.
  - 예: `RPUSH key value1 value2` 실행 시 `value1`, `value2` 순으로 저장된다.
- 단일 요소 추가는 $O(1)$, $N$개 요소 추가는 $O(N)$의 시간 복잡도를 가진다.
- 키가 존재하지 않으면 **빈 리스트를 생성**한 뒤 요소를 추가하고, String이나 Set 등 다른 타입의 키가 이미 존재하면 **에러가 발생**한다.

#### 데이터 추출 및 삭제 (`LPOP`, `RPOP`)

- **`LPOP`**: Head(맨 앞)에서 요소를 제거하고 반환한다. (Redis 6.2 이상부터 제거할 `count` 지정 가능)
- **`RPOP`**: Tail(맨 뒤)에서 요소를 제거하고 반환한다.
- 단일 요소 제거 연산은 $O(1)$ 복잡도를 가진다.
- 요소를 추출하여 리스트가 비어있게 되면 메모리 관리를 위해 **해당 키를 자동으로 삭제**한다.

#### 데이터 범위 조회 (`LRANGE`)

- **`LRANGE`**: 지정한 `start`와 `stop` 범위의 요소 목록을 조회한다. (두 인덱스 모두 포함)
  - 음수 인덱스 지원: `-1`은 리스트의 마지막 요소를 의미한다. (예: `LRANGE mylist 0 -1`은 전체 조회)
  - 존재하지 않는 인덱스 범위를 지정해도 에러가 발생하지 않으며 가용 범위 내 데이터만 반환한다.
- 시간 복잡도는 $O(S + N)$이다. ($S$: 시작 인덱스까지 이동 거리, $N$: 반환할 요소 개수)
- 연결 리스트 특성상 양 끝단 접근은 빠르나, 대용량 리스트의 **중간 위치 조회 시 성능 저하**가 발생할 수 있다.

#### 리스트 정보 조회 (`LLEN`, `LINDEX`)

- **`LLEN`**: 리스트의 전체 길이를 반환하며, 메타데이터를 직접 참조하므로 **$O(1)$의 즉시 반환 성능**을 보장한다. (작업 큐 대기 건수 파악에 용이)
- **`LINDEX`**: 특정 인덱스 위치의 요소 값을 조회한다. ($O(N)$ 복잡도)
  - Head부터 포인터를 타고 이동하므로 **양 끝단에 가까운 인덱스 조회**에 유리하며, 범위를 벗어나면 `nil`을 반환한다.

### 7.4. List 활용 패턴

- 애플리케이션 개발 시 표준 자료구조인 **큐(Queue)** 또는 **스택(Stack)** 을 구현하는 데 주로 사용된다.
- **큐 (Queue / FIFO)**:
  - `RPUSH` + `LPOP` 또는 `LPUSH` + `RPOP` 조합 사용
  - 생산자-소비자(Producer-Consumer) 패턴 구현 시 활용
- **스택 (Stack / LIFO)**:
  - `LPUSH` + `LPOP` 또는 `RPUSH` + `RPOP` 조합 사용
  - 최근 방문 이력 관리, 실행 취소(Undo) 등에 활용

#### Blocking POP

- `BLPOP` 및 `BRPOP`은 일반 POP 명령어의 **블로킹(Blocking) 버전**이다.
- 지정한 리스트가 비어있을 때 즉시 `nil`을 반환하지 않고, 새로운 **요소가 추가될 때까지 대기(Wait)** 상태에 들어간다.
- 예: `BLPOP queue 0` 실행 시 `queue`에 데이터가 들어올 때까지 타임아웃 없이 무한 대기한다.
- 다중 리스트 모니터링이 가능하며(`BLPOP queue1 queue2 0`), 이를 통해 **시스템 간 결합도를 낮추는 이벤트 기반 작업 큐**를 손쉽게 구현할 수 있다.
- 대기 상태 동안 **클라이언트 커넥션을 블로킹 방식으로 점유**한다.
  - 따라서 동일한 커넥션(클라이언트) 내에서는 `BLPOP` 응답을 받기 전까지 후속 명령어를 실행할 수 없다.

## 8. Set 타입

- **중복되지 않는 문자열 값들의 집합**이다.
- 동일한 값을 여러 번 추가하더라도 Set 내부에는 단 하나의 값만 저장된다.
- **순서를 보장하지 않는다**.
  - 요소를 추가한 순서가 유지되지 않으며, 내부 해싱 처리로 인해 저장 순서를 예측할 수 없다.

### 8.1. 내부 인코딩 방식

- **intset**:
  - 모든 요소가 정수이고, 요소 개수가 설정값(`set-max-intset-entries`) 미만이며, 모든 요소가 64비트 정수로 표현될 때 사용된다.
  - 정렬된 정수 배열 구조로, 이진 탐색을 사용하여 **$O(\log N)$의 시간 복잡도**로 검색한다.
- **hashtable**:
  - 요소 개수가 많거나 정수가 아닌 문자열 값이 포함되어 있을 때 사용된다.
  - 각 요소를 해시 버킷에 매핑하는 방식이며, 검색·삽입·삭제 연산 시 **평균 $O(1)$의 시간 복잡도**를 제공한다.
- **저장 용량 및 메모리 특성**:
  - 최대 **$2^{32} - 1$개**(약 42억 개)의 요소를 저장할 수 있으나 가용 메모리 한계를 고려해야 한다.
  - 해시 테이블의 구조적 오버헤드로 인해 동일 데이터 수 대비 List 구조보다 **메모리를 더 많이 소모**한다.

### 8.2. 주요 특징 및 장점

- **$O(1)$의 빠른 존재 여부 확인**:
  - List 구조가 데이터 존재 확인 시 전체 요소를 순회해야 하는 반면, Set은 $O(1)$ 복잡도로 즉시 확인할 수 있는 것이 가장 큰 장점이다.

### 8.3. 주요 명령어

#### 데이터 추가 (SADD)

- `SADD <Key> <Member> [Member ...]` 형태로 단일 또는 다중 요소를 추가한다.
- 실제로 **신규 추가된 요소의 개수를 반환**하며, 이미 존재하던 값을 추가하면 무시되고 `0`을 반환한다.
- 시간 복잡도는 추가하려는 요소 개수 $N$에 비례하는 **$O(N)$** 이다. (기존 Set의 크기와 무관)
- 키가 존재하지 않는 경우 빈 Set을 자동 생성한 후 요소를 추가한다.

#### 데이터 제거 (SREM)

- `SREM <Key> <Member> [Member ...]` 형태로 존재하는 요소만 제거하며, **실제 삭제된 요소 개수를 반환**한다. (해당 요소가 없으면 `0` 반환)
- 시간 복잡도는 제거 대상 요소 개수 $N$에 비례하는 **$O(N)$** 이다.
- 지정한 키가 존재하지 않아도 에러가 발생하지 않으며 `0`을 반환한다.
- 모든 요소가 삭제되어 빈 Set이 되면 List와 동일하게 **키 자체가 자동으로 삭제**된다.

#### 전체 조회 (SMEMBERS)

- `SMEMBERS <Key>` 형태로 Set에 포함된 모든 요소를 배열 형태로 반환한다.
- 반환 순서는 보장되지 않으므로 애플리케이션 영역에서 순서에 의존해서는 안 된다.
- 시간 복잡도는 전체 요소 개수 $N$에 비례하는 **$O(N)$** 이다.
- **주의사항**:
  - 단일 스레드 구조 특성상 대용량 Set에 `SMEMBERS` 실행 시 다른 작업이 블로킹될 수 있다.
  - 대규모 데이터 조회 시 커서 기반의 **`SSCAN` 명령어 사용을 권장**한다.

#### 요소 개수 조회 (SCARD)

- `SCARD <Key>` 형태로 Set에 포함된 전체 요소 개수를 반환한다.
- 시간 복잡도는 **$O(1)$** 이다. (요소를 순회하지 않고 내부 카운트 값을 바로 반환)
- 키가 존재하지 않으면 `0`을 반환한다.

#### 무작위 요소 추출 및 제거 (SPOP)

- `SPOP <Key> [Count]` 형태로 Set에서 요소를 무작위로 꺼내면서 **동시에 제거**한다.
- `Count`를 지정하지 않으면 단일 요소를 반환하고, 지정하면 해당 개수만큼 배열로 반환한다.
- 시간 복잡도는 `Count` 미지정 시 **$O(1)$**, 지정 시 **$O(N)$** 이다. ($N$: 실제로 꺼내는 요소 개수, `Count`와 Set 크기 중 작은 값)
- 키가 존재하지 않으면 `Count` 미지정 시 `nil`, 지정 시 빈 배열을 반환한다.
- 모든 요소가 제거되어 빈 Set이 되면 SREM과 마찬가지로 **키 자체가 자동으로 삭제**된다.

#### 무작위 요소 추출 (SRANDMEMBER)

- `SRANDMEMBER <Key> [Count]` 형태로 Set에서 요소를 무작위로 반환하지만, **SPOP과 달리 원본 Set을 변경하지 않는다.**
- `Count`가 **양수**이면 중복 없이 최대 `Count`개(Set 크기 초과 시 전체 요소)를 반환한다.
- `Count`가 **음수**이면 중복을 허용하여 `|Count|`개를 반환한다. (같은 요소가 여러 번 뽑힐 수 있음)
- `Count`를 지정하지 않으면 단일 요소를 반환한다.
- 시간 복잡도는 **$O(N)$** 이다. ($N$: 반환하는 요소 개수, `Count` 절댓값 기준)

#### 존재 여부 확인 (SISMEMBER, SMISMEMBER)

- `SISMEMBER <Key> <Member>`: 특정 값이 Set 내에 존재하는지 확인하며, 존재 시 `1`, 미존재 시 `0`을 반환한다. (**$O(1)$ 시간 복잡도**)
- `SMISMEMBER <Key> <Member> [Member ...]` (Redis 6.2+): 여러 멤버의 존재 여부를 **한 번에 확인**하여 각 멤버별 결과를 배열로 반환한다.

### 8.4. 집합 연산 명령어

#### 교집합 (SINTER)

- `SINTER <Key> [Key ...]` 형태로 둘 이상의 Set 간 **공통 요소(교집합)** 를 반환한다.
- 시간 복잡도: **$O(N \times M)$** ($N$: 가장 작은 Set의 크기, $M$: 비교할 Set의 개수)

#### 합집합 (SUNION)

- `SUNION <Key> [Key ...]` 형태로 둘 이상의 Set에 존재하는 **모든 요소의 합(합집합)** 을 반환한다.
- 시간 복잡도: **$O(N)$** ($N$: 모든 Set에 포함된 전체 요소 수의 합)

#### 차집합 (SDIFF)

- `SDIFF <Key> [Key ...]` 형태로 첫 번째 Set을 기준으로 다른 Set들과의 **차이 요소(차집합)** 를 반환한다.
- 시간 복잡도: **$O(N)$** ($N$: 첫 번째 Set의 모든 요소 수)

## 9. Hash 타입

- 필드와 값(Field-Value)의 쌍으로 구성된 데이터 컬렉션이다.
- 하나의 키 안에 여러 개의 필드를 저장할 수 있어 객체(Object), 해시맵(HashMap), 딕셔너리(Dictionary) 구조를 표현하기에 적합하다.
- 관계형 데이터베이스(RDB)의 테이블 **단일 행(Row)** 과 유사한 구조를 가진다.
  - 예: `user:1000` 키 내부의 `name`, `email`, `age` 필드 저장
- 모든 필드와 값은 **문자열(String) 기반**이며, **바이너리 세이프(Binary Safe)** 를 지원하므로 어떠한 데이터 형태도 저장 가능하다.

### 9.1. 내부 인코딩 방식

- **listpack** (Redis 7.0 이전의 `ziplist` 대체):
  - 필드와 값을 연속된 메모리 공간에 순차 배치하는 압축 인코딩 방식이다.
  - 다음 두 가지 조건을 모두 충족할 때 사용된다.
    - 필드 개수가 `hash-max-listpack-entries` 설정값 이하일 때 (기본값: 512개)
    - 모든 필드명과 값의 크기가 `hash-max-listpack-value` 설정값 이하일 때 (기본값: 64바이트)
  - 순차 탐색을 수행하므로 접근 시간 복잡도는 $O(N)$이지만, 요소의 크기가 작아 매우 빠른 속도와 높은 메모리 절감 효과를 제공한다.
- **hashtable**:
  - 필드명을 해시 함수로 계산하여 버킷에 저장하는 표준 방식으로, 메모리 사용량은 늘어나지만 **$O(1)$의 빠른 필드 접근 속도**를 보장한다.
- **저장 용량 및 활용**:
  - 단일 Hash 키에는 최대 **$2^{32} - 1$개**(약 42억 개)의 필드를 저장할 수 있으나 가용 메모리 한계를 고려해야 한다.
  - 실무에서는 하나의 객체를 표현하는 용도로 쓰이므로 단일 키에 수백만 개의 필드를 저장하는 경우는 드물다.

### 9.2. String 타입 대비 메모리 효율성

- 데이터를 여러 개개의 String 키(`user:1000:name`, `user:1000:email`)로 저장하는 대신 **단일 Hash 키(`user:1000`)** 로 관리하는 것이 메모리 측면에서 훨씬 유리하다.
- 개별 String 키는 키마다 독립적인 **Redis 메타데이터 오버헤드**가 생성되지만, Hash 구조를 활용하면 **단 1개의 메타데이터만 생성**되어 메모리 소모를 크게 줄일 수 있다.

### 9.3. 주요 명령어

#### 데이터 설정 및 수정 (HSET)

- `HSET <Key> <Field> <Value> [Field Value ...]` 형태로 단일 또는 다중 필드를 설정한다.
- 지정한 필드가 존재하지 않으면 **자동 생성**하고, 이미 존재하면 **값을 덮어쓴다**.
- **반환값**: 새로 추가된 필드의 개수를 반환한다. (기존 필드 값 업데이트 시 `0` 반환)
- Redis 4.0 이상부터 단일 `HSET` 명령어로 다중 필드 설정이 가능해져 과거의 `HMSET` 명령어를 대체한다.
- 시간 복잡도: 설정할 필드 수 $N$에 비례하는 **$O(N)$** (단일 필드 설정 시 $O(1)$, listpack 인코딩 시 내부 순차 탐색 수행)

#### 데이터 조회 (HGET, HMGET)

- **`HGET`**: `HGET <Key> <Field>` 형태로 단일 필드 값을 조회한다. ($O(1)$ 복잡도, 미존재 시 `nil` 반환)
- **`HMGET`**: `HMGET <Key> <Field> [Field ...]` 형태로 여러 필드 값을 요청 순서에 맞게 배열로 반환한다.
  - 네트워크 RTT를 단축시키는 다중 조회 명령어로, 미존재 필드 위치에는 `nil`이 응답된다. ($O(N)$ 복잡도)

#### 숫자 연산 (HINCRBY, HINCRBYFLOAT)

- **`HINCRBY`**: `HINCRBY <Key> <Field> <Increment>` 형태로 지정한 필드의 정수값을 원자적으로 증가 또는 감소시킨다. (필드 미존재 시 `0`으로 초기화 후 연산, 경쟁 상태 예방)
- **`HINCRBYFLOAT`**: 지정한 필드의 실수(Float) 값을 원자적으로 증가 또는 감소시킨다.

#### 필드 검사 및 전체 조회 (HEXISTS, HKEYS, HVALS)

- **`HEXISTS`**: `HEXISTS <Key> <Field>` 형태로 Hash 내 특정 필드의 존재 여부를 확인한다. (존재 시 `1`, 미존재 시 `0` 반환)
- **`HKEYS`**: 지정한 Hash 내의 **모든 필드명**을 배열로 반환한다. (순서 보장 안 됨)
- **`HVALS`**: 지정한 Hash 내의 **모든 값**을 배열로 반환한다. (순서 보장 안 됨)

## 10. Sorted Set 타입

### 10.1. 개요

- 기본적인 Set과 마찬가지로 **중복되지 않는 요소**를 저장하지만, 각 요소마다 **score**라는 숫자 값을 함께 가진다는 차이가 있다.
- 이 score를 기준으로 요소들이 **자동으로 정렬**되기 때문에, 게임 전투력 순위나 월별 거래 금액 순위처럼 **랭킹을 집계**해야 하는 상황에서 대표적으로 활용된다.
- Sorted Set의 각 요소는 **멤버(Member)** 와 **스코어(Score)** 두 부분으로 구성된다.
  - 멤버: 실제 저장되는 문자열 값이다.
  - 스코어: 정렬 기준이 되는 부동소수점 숫자 값이다.
  - 예: 게임 리더보드에서 사용자 이름이 멤버, 점수가 스코어에 해당한다.
- Sorted Set은 항상 **스코어 순서로 정렬된 상태**를 유지한다.
- 새 요소를 추가하면 Redis가 트리 구조처럼 **자동으로 정렬 위치를 찾아 삽입**하므로, 별도의 정렬 작업을 수행할 필요가 없다.
- 스코어가 동일한 요소들은 **멤버의 사전 순(Lexicographic Order)** 으로 정렬된다.

### 10.2. 내부 인코딩 방식

- **listpack**: 요소 개수와 크기가 작을 때 사용되는 압축 인코딩 방식이다. (Hash 타입에서 다룬 방식과 동일하므로 설명은 생략한다.)
- **skiplist**: 설정된 임계값을 초과하면 사용되는 방식으로, 실제로는 **스킵 리스트와 해시 테이블을 결합한 이중 구조**이다.
  - 스킵 리스트는 여러 레벨의 포인터를 유지하여 **$O(\log N)$**의 빠른 검색 속도를 지원하며, **스코어 기반 조회**에 사용된다.
  - 해시 테이블은 **멤버 기반 조회**에 사용된다.
  - 두 구조를 동시에 유지하므로 메모리 사용량은 늘어나지만, 다양한 연산을 효율적으로 수행하기 위한 트레이드오프로 이해하면 된다.
- **저장 용량 및 메모리 특성**
  - 단일 Sorted Set 키에는 최대 **$2^{32} - 1$개**(약 42억 개)의 요소를 저장할 수 있으나, 실제로는 가용 메모리를 고려해야 한다.
  - 스킵 리스트와 해시 테이블을 함께 유지하는 것이 일반적이므로, 각 요소마다 멤버·스코어·스킵 리스트의 여러 레벨 포인터를 모두 저장해야 한다.
  - 그 결과 **일반 Set보다 약 2~3배 이상 많은 메모리**를 사용한다.

### 10.3. 주요 명령어

#### 데이터 추가 (ZADD)

- `ZADD <Key> <Score> <Member> [Score Member ...]` 형태로 스코어와 멤버 쌍을 지정하여 Sorted Set에 요소를 추가한다.
- 지정한 Sorted Set이나 멤버가 존재하지 않으면 **자동으로 생성**된다.
- **반환값**: 새로 추가된 요소의 개수만 반환한다. (기존 요소의 스코어를 업데이트한 경우는 포함되지 않는다.)
- 예: `ZADD leaderboard 100 Alice` 실행 시, leaderboard라는 Sorted Set에 Alice라는 멤버가 스코어 100으로 추가된다.
- 여러 개의 스코어-멤버 쌍을 한 번에 추가하는 것도 가능하며, 이 경우 새로 생성된 요소의 개수만 반환된다.
- ZADD는 다음과 같은 다양한 옵션을 지원하며, 특수한 상황이 아니라면 기본형만 사용해도 충분하다.
  - **NX**: 멤버가 존재하지 않을 때만 추가한다. (`SETNX`와 유사한 개념)
  - **XX**: 멤버가 이미 존재할 때만 값을 업데이트한다.
  - **GT**: 새로운 스코어가 기존 스코어보다 **클 때만** 업데이트한다. (더 높은 점수로만 갱신하고 싶을 때 유용하다.)
  - **LT**: 새로운 스코어가 기존 스코어보다 **작을 때만** 업데이트한다. (GT의 반대 개념이다.)
  - **CH**: 반환값의 기준을 바꾸는 옵션으로, 새로 추가된 요소뿐 아니라 **스코어가 변경된 요소까지 개수에 포함**한다.
  - **INCR**: `ZINCRBY`처럼 동작하며, 지정한 만큼 스코어를 증가시키고 **새로운 스코어 값을 반환**한다.

#### 멤버 개수 조회 (ZCARD)

- `ZCARD <Key>` 형태로 Sorted Set에 저장된 **전체 멤버 개수**를 조회한다.
- 반환값은 **정수**이며, 키가 존재하지 않으면 `0`을 반환한다.
- 예: `ZCARD leaderboard` 실행 시, leaderboard에 저장된 멤버 수가 반환된다.

#### 점수 단건 조회 (ZSCORE)

- `ZSCORE <Key> <Member>` 형태로 특정 멤버의 **스코어 값**을 조회한다.
- 멤버가 존재하지 않으면 `nil`을 반환하며, 존재하는 경우 스코어는 **문자열**로 반환된다.
- 여러 멤버의 점수를 한 번에 조회하고 싶다면 `ZMSCORE`를 사용할 수도 있다.
- 예: `ZSCORE leaderboard Alice` 실행 시, Alice의 현재 스코어가 반환된다.

#### 범위 조회 (ZRANGE, ZREVRANGE)

- **`ZRANGE`**: `ZRANGE <Key> <Start> <Stop> [WITHSCORES]` 형태로 지정한 **순위 범위**의 요소를 반환한다.
  - Start와 Stop은 순위를 나타내는 인덱스이며, 순위는 **0부터 시작**한다.
  - 스코어가 **가장 낮은 요소가 순위 0**이며, 그다음으로 낮은 요소가 순위 1인 식으로 이어진다.
  - 음수 인덱스도 사용할 수 있으며, `-1`은 스코어가 가장 높은 마지막 요소를 의미한다.
  - 예: `ZRANGE leaderboard 0 2`를 실행하면 스코어가 가장 낮은 3개의 요소가 낮은 순서대로 반환된다.
  - 기본적으로는 스코어를 반환하지 않으며, 스코어까지 함께 받고 싶다면 `WITHSCORES` 옵션을 추가하면 된다.
  - 반환되는 스코어는 항상 **문자열**로 반환된다. (정수 스코어는 `"100"`, 소수 스코어는 `"100.5"` 형태이다.)
- **`ZREVRANGE`**: `ZRANGE`와 반대 개념으로, 스코어가 **가장 높은 요소부터 낮은 순서**로 반환한다.
  - 순위 0은 **스코어가 가장 높은 요소**를 의미한다.
  - `ZRANGE`와 `ZREVRANGE`는 서로 반대 방향으로 동작하므로, 실무에서는 둘 중 하나만 사용해도 데이터를 가져오는 데 문제가 없다.
- **ZRANGE의 REV 옵션 (Redis 6.2+)**: `ZRANGE <Key> <Start> <Stop> REV [WITHSCORES]` 형태로 `REV` 옵션을 지정하면, 별도의 `ZREVRANGE` 명령어 없이도 **내림차순 조회**가 가능하다.
  - 즉, `ZREVRANGE key 0 2`와 `ZRANGE key 0 2 REV`는 동일한 결과를 반환한다.
  - 최신 버전에서는 `ZRANGE`에 `BYSCORE`, `BYLEX`, `REV`, `LIMIT` 등의 옵션을 결합해 `ZREVRANGE`, `ZRANGEBYSCORE`, `ZREVRANGEBYSCORE` 등 기존 명령어들을 하나로 통합해서 사용할 수 있다.

#### 순위 조회 (ZRANK, ZREVRANK)

- **`ZRANK`**: `ZRANK <Key> <Member>` 형태로 특정 멤버의 **순위**를 조회한다. (인덱스 기반 조회가 아니라 멤버 기반 조회라는 점에서 ZRANGE와 다르다.)
  - 순위는 0부터 시작하며, **스코어가 낮은 것부터 순서대로 계산**된다.
  - 멤버가 존재하지 않으면 `nil`이 반환되며, 순위는 **정수**로 반환된다.
- **`ZREVRANK`**: `ZRANK`와 반대로 **스코어가 높은 것부터 낮은 순서**로 순위를 계산한다.
  - 리더보드에서 **상위 순위를 표현**할 때 많이 사용된다. (게임에서 가장 높은 점수가 1등으로 표시되는 경우 등)
- Redis 7.2 이상 버전부터는 `ZRANK`와 `ZREVRANK`에 **`WITHSCORE`** 옵션이 추가되어, 순위와 스코어를 함께 조회할 수 있다.

#### 스코어 증가 (ZINCRBY)

- `ZINCRBY <Key> <Increment> <Member>` 형태로 지정한 멤버의 스코어를 **원자적으로 증가**시킨다.
- **반환값**: 기존 스코어에 증가값을 더한 **새로운 스코어**를 반환한다.
- 예: `ZINCRBY leaderboard 10 Alice` 실행 시, 기존 스코어가 100이었다면 110으로 증가한다.
- 멤버가 Set에 존재하지 않았다면 기존 스코어를 0으로 간주하고 증가값만큼의 스코어를 가지게 된다.

#### 요소 삭제 (ZREM)

- `ZREM <Key> <Member> [Member ...]` 형태로 Sorted Set에서 불필요한 요소를 삭제한다.
- 멤버를 여러 개 지정하여 한 번에 삭제하는 것도 가능하다.
- **반환값**: 실제로 삭제된 멤버의 개수를 반환한다.
- 예: `ZREM leaderboard Alice` 실행 시, leaderboard Sorted Set에서 Alice 요소가 삭제된다.
- 마지막 요소까지 삭제되어 Sorted Set이 완전히 비게 되면, 해당 키는 **자동으로 삭제**된다.
- 이 외에도 순위 범위를 기준으로 요소를 삭제하는 **`ZREMRANGEBYRANK`** 와 같은 명령어도 존재하므로, 좀 더 복잡한 삭제 로직이 필요할 때 참고하면 좋다.

#### 점수 구간 삭제 (ZREMRANGEBYSCORE)

- `ZREMRANGEBYSCORE <Key> <Min> <Max>` 형태로 **지정한 스코어 범위**에 속하는 요소를 모두 삭제한다.
- `ZREMRANGEBYRANK`가 순위(인덱스) 기준으로 삭제하는 것과 달리, 이 명령어는 **스코어 값 자체**를 기준으로 삭제한다.
- **반환값**: 실제로 삭제된 멤버의 개수를 반환한다.
- 예: `ZREMRANGEBYSCORE leaderboard 0 90` 실행 시, 스코어가 0 이상 90 이하인 모든 멤버가 삭제된다.
- 최소/최대값에 `-inf`, `+inf`를 사용하면 무한대 범위를 지정할 수도 있다.
